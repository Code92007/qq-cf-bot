# 三工程联动：内部使用简化版

2026-10-09，v4。替代此前 v3，首版按本文实现；运维步骤见 [cpc-integration-operations.md](../../cpc-integration-operations.md)。

## 1. 只做必要闭环

| 工程 | 负责什么 |
| --- | --- |
| dlut-cpc | 人员档案、每场确认名单、成员认领审核 |
| oj-submission-wall | 线上提交、经过管理员核验的现场逐题结果、区域赛覆盖 |
| cf-bot | 口胡记录、练习、合并代码与现场进度后的避题 |

数据流：dlut-cpc 的名单和认领结果 → oj-wall 的代码/现场进度 → cf-bot。每个工程保留独立数据库，页面读取本地结果。

首版不做 SSO、OAuth、成员密码系统、消息队列、增量事件、自动模糊匹配或新的中心服务。增加少量 SQLite 表、几个 HTTP 接口和管理员命令即可。

## 2. 成员认证与关联

1. 用户登录 oj-wall，在区域赛页选择 dlut-cpc 成员、提交核验说明。
2. 管理员通过 dlut-cpc 的命令查看申请，线下核验后批准、拒绝或撤销。复用已有成员和逐场名单，不重造人员库。
3. oj-wall 定期读取审批结果，将现场队伍成绩归给该成员对应的 oj-wall 账号。一个成员只允许一个有效认证主账号。
4. 用户在 oj-wall 生成本人只读连接码，在自己的 cf-bot 区域赛页粘贴一次，完成进度关联。

连接码仅能读取该 oj-wall 用户的区域赛进度；有效期 180 天，重新生成或撤销使旧码失效。没有成员认证也能关联自己的线上记录。cf-bot 不接触认领材料，不要求再次真人认证。

认领审批与用户登录分开：dlut-cpc 决定“这个账号是否对应该成员”，oj-wall 现有登录让用户持续证明自己控制这个账号。无法找回账号时管理员先撤销旧关联，再核验新申请。

## 3. 四种通过来源，分别统计

- P：个人线上账号通过。
- T：用户主动绑定的线上团队账号通过。
- S：用户在该场确认所属队伍的现场通过。
- O：cf-bot 的口胡通过。

| 视角 | 统计集合 |
| --- | --- |
| oj-wall 默认区域赛覆盖 | P ∪ S |
| oj-wall 勾选包括线上团队 | P ∪ T ∪ S |
| cf-bot 默认综合视角及“未完成”过滤 | P ∪ T ∪ S ∪ O |
| cf-bot 代码视角 | P ∪ T，现场另标 |
| cf-bot 口胡视角 | O |

逐题去重；题格区分个人、团队和现场。现有 cf-bot QOJ 团队通过继续有效。oj-wall 提供账号类型选择，明显的 ucup-team 自动标为团队，其他账号由用户确认。

接口中的 personal/team/onsite 布尔值仅表示是否存在有效通过证据，false 表示暂无证据，不证明未做过。首版覆盖状态统一为 partial，页面明确提示历史待补；不构造“已查全但未通过”的结论。

现场队伍通过不冒充本人独立 AC，不生成虚假的个人提交或时间，也不影响现有线上热力图、连续训练天数和奖牌统计。口胡记录只保存在 cf-bot。

## 4. 现场榜单先人工核验导入

dlut-cpc 发布已确认的逐场成员关系，包括无奖牌/奖项待确认的参赛记录。oj-wall 管理员选择其中一条参赛记录，核对真实榜单的队伍行、比赛与题序映射，再通过文件导入通过题列表。

导入文件保留 participation_id、contest_id、队名、来源链接、榜单行标识和通过题号，可附原始榜单行/截图说明。未核验的映射、无逐题结果的总解题数、相似队名不能自动用于完成统计。

同一来源/队伍行重新导入会替换该条证据，保留导入历史；支持撤销。重判取消一条 AC 后按其他有效证据重算。名单纠错由 dlut-cpc 负责，榜单结果纠错由 oj-wall 负责。

首版不实现 XCPCBoard/RankLand 自动抓取适配器。先用几场经过核验的榜单跑通；后续自动适配器也应写入相同证据结构，无须改动 cf-bot。

## 5. 同步与目录

- 名单及审批、用户进度均使用完整快照，不实现 ETag、游标、事件日志或复杂版本切换。
- 每 5 分钟后台拉取；用户可手动安排刷新。提交认领、首次连接允许一次短超时请求，普通页面请求不等待外站。
- 快照核对 schema、发布方 UUID、结构与数量后，事务替换远端缓存。失败保留最后成功结果，不当空集合清库。
- 明确撤销的认证移除现场归属；撤销连接码时 cf-bot 下一次同步清除该关联投影。超过 24 小时无法核验授权，暂停远端投影的统计和避题作用。
- 现场资格截止时间来自 dlut-cpc 最后成功同步，不能靠刷新 oj-wall 无限续期。恢复服务后重新同步即可。
- 公共题目目录沿用现有 JSON，作为同一版本的数据文件分别打包进两个工程；用文件哈希核对，无在线目录依赖。未知题目 ID 留在原快照中，目录补齐后重新聚合。

保留现有 cf-bot 绑定和同步，首版不做复杂的数据交接。重复来源按题去重；同一用户选择继续使用本地与远端两份证据时，两份来源分别保留，断开远端不会删除本地证据。关闭某账号重复抓取属于后续迁移工作。

## 6. 最小接口和持久数据

| 发布方 | 接口 |
| --- | --- |
| dlut-cpc | 受服务凭据保护的 roster/snapshot、claims/snapshot、claims 提交、meta |
| oj-wall | 登录用户自己的成员申请、账号类型、生成/撤销连接码、区域赛查询 |
| oj-wall | Bearer 连接码保护的 me/progress/snapshot |
| cf-bot | 本站会话与 CSRF 保护的 wall-connect、wall-disconnect、wall-sync |

服务间名单/认领采用管理员配置的同步凭据；用户进度采用单用户只读码，二者不混用。生成连接码等 oj-wall 写操作检查 Origin。凭据只存服务端，不放查询参数或浏览器本地存储。

新增数据局限于稳定 ID 映射、认领及审核日志、来源快照、现场证据及历史、只读码校验记录、cf-bot 关联及进度缓存。现有业务表继续使用。

## 7. 迁移必须可用

每个逻辑服务持久保存 authority_id；人员、用户主体及参赛记录具有持久 UUID 映射。它们与 IP、域名、容器及本地自增主键分开。搬迁后读取原 ID，不重新生成。

地址和预期信源 UUID 通过配置提供，支持同机私网或不同主机 HTTPS。数据备份包含三个 SQLite 主库、外部榜单证据、目录文件、同步凭据及 cf-bot 持有的连接码；使用 SQLite 一致备份，不只复制活跃主文件遗漏 WAL。

首版只承诺整个运行库及必要文件的迁移，不建设通用跨数据库逻辑导入系统。换域名更新公开/API 地址和浏览器脚本目标配置；未到期且完整恢复的连接码继续有效，不需要重新真人审核。丢失连接码时重新生成关联即可，人员认领不重做。

搬迁时停止被迁服务写入 → 一致备份 → 新机恢复和核对 UUID → 停旧实例并切换地址 → 全量同步。一个 authority_id 同时只有一个生产写入端，不从 seed 重建后冒充原站点。新独立站点使用新 UUID。

## 8. 首版验收

- 登录申请 → 管理员批准 → 现场通过出现在 oj-wall → 粘贴连接码后出现在 cf-bot 综合视角。
- 个人/团队/现场/口胡来源正确，重复题只计一次，现场不冒充代码或口胡。
- 不同用户不串记录，旧连接码撤销/更换后失效。
- 认领撤销、榜单更正或撤销会重算；传输失败保留成功缓存。
- 复制三个数据库到新目录后，服务 UUID、成员 UUID、认领及连接关系不变。
- 现有账号绑定、QOJ 导入和口胡草稿继续可用。
